01 / Builds

The four builds

Each build runs on its own subdomain, never a shared path, so builds can't share cookies or storage and skew the session and CSRF tests.

03 / Method

Ten steps

The test plan is written and committed before any build exists, so nothing we see in the code can shape how we test it.

  1. Lock the specPick the models and coding tool, write the feature list, base prompt and security line.
  2. Write and lock the test planExact steps and payloads for every test, committed to the repo first.
  3. Generate the 4 buildsFresh session per build. Every prompt and follow-up logged word for word.
  4. Check feature parityOne logged follow-up per missing feature, and never one about security.
  5. Deploy in the labOwn subdomain, database and storage per build, with identical seed data.
  6. Run automated scansOWASP ZAP, Semgrep, gitleaks and npm audit, saving the raw output.
  7. Run the manual testsThe same checklist in Burp Suite, in the same order, with screenshots.
  8. Classify the findingsFill the results grid, sort findings, rate confirmed vulns with CVSS 3.1.
  9. Remediate and retestFor the 5–7 most meaningful vulns: exploit, fix, rerun the same test.
  10. Write up and presentReport, exploit demos, prompt log and the results grid.

Toolkit

  • OWASP ZAP for automated scanning
  • Burp Suite for manual testing (Repeater, Intruder)
  • Semgrep for static code analysis
  • gitleaks for secret scanning
  • npm audit for dependency checks

Framework

  • OWASP Web Security Testing Guide (WSTG)
  • OWASP Top 10 (2021)
  • CVSS 3.1 for severity ratings
  • Scanners catch surface issues; Burp catches the logic flaws they miss

06 / Scope

Limits

In scope

  • The app's own code: auth, sessions, access control, database queries, input handling, file uploads and secrets

Out of scope

  • Cloudflare's infrastructure and the database provider itself. We test how the app uses them, not the platforms.
  • This homepage: a hand-built static directory, not a test subject

Limitations

  • AI output varies run to run, so each build is one sample, not a guarantee.
  • Two models only; results may not hold for other tools.
  • The stack may block some vulns by default (e.g. prepared statements), which we note where it happens.
  • Manual testing depends on our skill; the locked checklist limits that bias.
